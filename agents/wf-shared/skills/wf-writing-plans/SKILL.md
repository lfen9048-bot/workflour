# Writing Plans · Workflour

在本项目 PLAN.md 中定稿，保留原始需求和研究来源。计划说明用户要完成的事、必要约束、验收条件、现有系统接口和风险；内部文件名、函数名、DOM/CSS 结构只在兼容性或并行边界确有需要时规定。主编码负责技术设计。

将目标、本次范围和优先级对应到可观察的验收结果：用户在什么条件下做什么，应得到什么结果；按实际风险覆盖失败、空状态或边界行为。避免“体验良好”“运行正常”这类无法判定的标准。优先级用于安排实现顺序与团队建议的取舍，不能把用户明确要求擅自降为可选项或推迟；新增范围和建议先标明来源，不冒充已确认需求。只有影响交付的未决问题才标为阻塞，能从已有材料确认的内容不再询问。

先由负责人写初案，方案评审只指出具体问题，负责人回应后形成一份定稿；不生成三份平行长方案。普通小页面/小工具的计划应短于实现说明，优先一页目标、验收、工作项和证据表。每项工作具有可检查结果，避免“完善细节”这类空项。

在这份计划中交接“目标／需求 → 工作项 → 验收方式”，完成后由负责人据实际结果关联证据。没有用户数据时不虚构商业指标、访谈或收益；不为填满模板强加目标数量、人物画像、长 PRD 或额外审批。需求有变化时按既有流程更新范围与交接，不能悄悄换掉原验收条件。

小任务仅一位主编码。只有能独立验收、写入范围不重叠的子任务才增加协作编码。新页面或重要视觉/交互方向变更先做关键页面可看版本，再继续完整实现；已认可方向的局部修复复用原结论，只验证受影响路径。使用既定 Plan/Code 原生委派和两轮总返工预算；本技能不要求其他框架、额外子代理、Git 提交、工作树或新的人类审批。
