# 按需检查错误路径

只追本次改动实际涉及的 I/O、异常处理、异步清理、重试或降级。先确定项目对成功、失败、用户取消、可选数据缺失的约定，再判断实现；`catch`、默认值、可选链本身不构成缺陷。

## 沿一次失败检查结果

从具体故障点追到最终调用者：谁捕获，返回什么，留下什么状态，用户或上层会看到什么。检查捕获范围是否把预期异常之外的编程错误、损坏数据、鉴权失败等变成正常结果。顶层统一捕获可以合理；它仍应保留失败状态、可诊断原因和必要清理，不必在每一层重复日志或弹窗。

有针对性地选择故障点，例如读取缺失文件、损坏内容、写入中断、超时或服务拒绝。使用项目现有测试入口、临时目录或局部故障注入；不需要请求真实付费模型、破坏用户数据或影响生产服务。mock 只替换不可控边界，断言真实的错误转换、返回状态及副作用。

## 判断容易混淆的分支

| 分支 | 应核对的约定与结果 |
| --- | --- |
| 用户取消 | 是否按约定终止后续工作、释放资源；不得仅因无错误弹窗而判为静默失败，也不能被误报为成功或触发新的工作。 |
| 可选文件或配置缺失 | 约定允许缺失时，默认值可以合理；文件损坏、权限拒绝与确实不存在是否被不恰当地混为一谈。 |
| 超时或连接中断 | 远端可能已经完成；是否在未核对结果时重复有副作用的操作。网络错误不自动等于额度耗尽。 |
| 重试 | 是否只针对可重试条件、次数有界，取消可停止等待，最终失败能到达调用者；没有幂等保护时不要假定重复执行安全。 |
| 降级 | 是否符合既定产品约定，保留所需能力与用户选择；必要时能说明实际采用的替代路径。不要把占位/模拟结果伪装成真实成功。 |
| 部分写入或清理失败 | 原有数据、提交标记、临时资源是否保持约定；清理异常是否遮盖主错误。只清理本次拥有的资源。 |

## 可观察与可诊断

失败是否到达适合的位置：CLI 退出码和 stderr、API 错误状态、界面提示或任务账本。已有上层提示足够时不要求底层重复报告。提示应区分用户能采取行动的原因；记录仅包含必要上下文，不写密钥、会话令牌或完整敏感请求。沿用项目日志接口，不引入固定 Sentry、Statsig 或其他监控依赖。

发现必须能说明“什么输入/故障 → 哪段处理 → 哪个错误结果 → 对用户有什么影响”。无法证实的路径标为待核实风险；合理取消、约定内缺省与有效降级不报为 Bug。不因为异常被捕获就统一定为严重缺陷。
