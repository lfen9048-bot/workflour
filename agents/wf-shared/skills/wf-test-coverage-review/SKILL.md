# 测试覆盖审核

用于独立审核或实施者自查：找出会漏掉真实缺陷的测试缺口，不追求百分之百覆盖率。先读取本轮需求、实际代码和已有测试；有可靠基线时查看差异，没有基线时对照需求检查相关完整模块，不要求先建 PR。

## 从行为找到缺口

把受影响的用户行为对应到具体测试和断言。重点追踪本轮改变的分支、输入边界、状态保存和调用者；异步、并发或恢复逻辑只有实际涉及才检查。已有集成测试能覆盖同一行为时，记录它，不再要求重复单测。

覆盖结论只限测试实际使用的输入、到达的分支和断言的结果；不能把相近场景或补充探针的证据归到原有测试名下。

逐项判断测试能否阻止一个具体错误。例如“存储写入失败却显示成功”比“应该增加错误测试”更有用。检查：

- 断言是否观察真实返回值、持久副作用或用户可见状态，而不是只验证 mock 被调用、源码字符串或照抄算法。
- fixture 是否能到达目标分支；否定用例是否会因无关异常而误通过。
- 边界两侧、无效输入、旧行为的兼容要求是否已有有效覆盖。不要因一个边界通过而宣称整个输入域通过。
- 取消、失败、重试或并发是否可能产生重复操作、部分写入或错误的完成状态；只针对实际存在的机制提出用例。

如果改动涉及外部调用、文件/数据库、异常捕获、重试、降级或异步清理，按需阅读 [错误路径检查](references/error-paths.md)。普通纯函数或文案修改不必加载。

## 证据与结论

先读取和运行已有相关测试，再对明确的缺口做最小复现或补充建议。同一缺陷已有直接、可复现证据就停止追加证明；只有还存在会改变判断的疑点，才增加另一种探针或真实环境复现。不为枚举可能性而检查契约外输入。复审复用有效探针，针对本轮变化和未关闭发现重跑；没有新风险时不扩大成整套测试重写。独立审核不擅自修改业务实现、安装测试框架或新增委派。

区分“已复现缺陷”和“尚无覆盖的风险”。只有缺少测试并不能证明产品已出错，也不自动成为阻断项。严重度按用户影响、触发条件和恢复代价判断；高风险契约确实缺乏验证时说明为何阻断，其余建议按价值排序。

优先使用当前任务指定的输出位置；普通项目未另指定时写入当前角色的审核记录。结论只汇总一次，包含被审快照、已有覆盖、具体缺口/缺陷、位置、触发输入、预期与实际及实际命令/结果。尚未关闭的问题给最小下一步，已解释的事实不反复展开。未运行或受环境阻碍的检查明确标注。只有未决事项仍影响验收时判为需修复或受阻；代码测试不能代替 Plan 的真实体验检查。
