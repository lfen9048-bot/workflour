# 复核与失败归因

## 属性是否真的有约束

查看测试调用的实际函数和断言，而不是只看 `@given`、`fc.property` 或测试数量：

- 恒真断言、结果与自身比较、无断言，或 mock 提供答案后再断言相同答案，不能检查产品正确性。
- 复制生产算法不构成独立参照；只检查类型、长度或“没报错”可能漏掉关键行为，缺口按契约与影响判断。
- 过滤条件相互矛盾、几乎全部拒绝或只剩一个输入，不能据测试通过宣称广泛覆盖。确认库实际执行了有效样例。
- 使用同一个可变对象比较前后、共享跨样例状态或无控制的时间/随机源，可能制造误通过或不稳定失败。
- 对浮点、排序稳定性、Unicode、序列化相等性的要求应来自实际契约。不要武断使用精确相等，也不要用过宽容差掩盖错误。

重复调用的相等性不总是无意义：若契约要求在相同输入与受控环境下稳定输出，且内部顺序/状态可能变化，它可验证确定性。反过来，函数本来就允许随时间变化时不应要求稳定。

## 最小反例意味着什么

先在当前快照单独重现，核对前置条件、fixture、生成域、真实返回值和属性依据，再分类：

| 证据 | 分类与处理 |
| --- | --- |
| 合法输入违反明确承诺 | 实现缺陷；保留反例、契约、预期/实际和复现命令，建立回归覆盖。 |
| 输入不在此属性的合法域 | 生成器问题；收窄该属性。若接口承诺拒绝该输入，另测拒绝行为，不能因此漏掉应有校验。 |
| 属性与约定冲突 | 测试问题；修正属性并解释依据，不为了变绿任意放宽期望。 |
| 边界行为没有约定，合理解释会改变用户结果 | 需求待定；向当前项目负责人提出具体选择与影响，不自行定义为产品 Bug。 |
| 仅在跨样例污染、错误 mock 或不受控环境下失败 | 测试隔离或环境问题；修复隔离，保留此前失败事实，再验证产品路径。 |

一个反例可证明某个承诺被违反；一次通过不能证明全部输入正确。测试质量问题、真实产品缺陷和需求不明确分开记录，严重度按实际用户影响，不照搬固定“恒真即 CRITICAL”等等级。
