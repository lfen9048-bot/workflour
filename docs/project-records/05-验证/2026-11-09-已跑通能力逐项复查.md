# 已跑通能力逐项复查

用户要求：逐项检查此前已宣称跑通的能力，确认 Harness 是否已经分成多个版本。本轮是复查，不新增自动编排或改变角色分工。

## Harness 分离结论

当前是一套 **DeepSeek Harness 0.2.1-rc.2** 程序，用不同 profile 启动不同 Agent，并非安装多个软件版本。

| 项目 | Coder | Doc |
| --- | --- | --- |
| 当前 ACP profile | omb-coder | omb-doc |
| 真实请求路由 | workbuddy / glm-5.3-flash | workbuddy / deepseek-v4.1-flash |
| 实际自动注入的 skills | 仅 code-assistant | 仅 doc-writer |

模型依据：当轮 request/header 与 request/context；skills 依据：当轮 user/message seq11 中 system-reminder 的 available_skills，未以模型自述作为判据。实际运行 patch 的模型、skills、persona 和禁用项与项目模板一致。

共享：dsh 可执行文件、默认 ~/.dsh、WorkBuddy 账号、desktop/node_modules 依赖、项目工作目录。旧 headless agent-coder/doc 仍保留，原六个基线文件 SHA-256 全部未变。

两个角色的配置分开，不代表每个角色有独立的系统权限边界。此次实测 Harness 的写工具会按当前工作目录实施 workspace-write 限制：写验证目录（在 cwd 外）被拒，经对已审查的具体写入操作批准一次后完成。两个角色仍可修改它们共用的工作目录。

### 必须保留的边界

- Gemini 首轮目录外 File 读取出现多次审批与额外文件查找；已主动中断，不把该次完整任务记成通过。改在 cwd 内用一次 shell 读取后，147秒结束（包含等待测试人员审批的时间），不能把147秒全部解释为模型计算时间。
- Gemini 的一分钟静默提示不是任务失败。native记录显示 cancel 已返回 cancelled、后续 load 成功、审批工具 completed；最终也有正确回复，因此没有证据判定为取消失效。
- 重启后保留历史与重建上下文，不代表完整恢复底层 Harness 原生会话。此次证实：聊天文本可以恢复，但未进入最终回复的工具结果细节不一定恢复；需要靠交接文件重新读取。源码核对：`dist-server/server/delta-context.js:17` 过滤掉工具 activity；`turn-context.js:18` 拼接聊天文本；`context-rebuild.js:56-80` 的可选工具历史也仅带工具名/目标/状态，不带结果。实查本次恢复prompt有恢复前言和结果文件路径，但不含fixture真实nonce。这解释本次现象，不是整个续聊失效。
- nohup 的退出发生于助手执行环境；本轮没有证明在用户普通终端启动时也会被回收。当前服务已恢复为持久前台终端，pidfile 同步实际健康检查PID；没有部署开机自启或新的后台守护。
- 手机蜂窝网络、新设备配对、手机审批按钮、本轮没有重新实操。沿用先前用户实测通过的历史证据，不能写成此次重测通过。
- 强制断开隧道后的自动重连本轮未重复；只确认当前隧道与VPS正常，之前有强制断开实测记录。
- 所有测试结束后 Coder/Doc/Gemini 仍为 ask，全部空闲；没有保存长期放行规则。
