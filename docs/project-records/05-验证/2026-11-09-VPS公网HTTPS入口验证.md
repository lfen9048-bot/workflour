## 1. 端口可达性（修正前置核验的未验证项）

前置核验只记录了"80/8080/9001 无监听"，没有验证公网防火墙是否放行。
本轮在 VPS 临时起响应服务实测：

| 端口 | 从 Mac 直连结果 |
| --- | --- |
| TCP 80 | `PROBE-OK`，HTTP 200 |
| TCP 8443 | `PROBE-OK`，HTTP 200 |

命令带 `--noproxy '*'` 绕过本机 Clash。

**对照组验证方法有效性**：`nc -z` 对不可路由的 `192.0.2.1:80` 也报"可达"，
说明被 TUN 劫持，其结论不可用。这是本轮的方法学修正。

## 3. 端到端接口

```text
GET https://your-public-host.example:8443/api/health
→ 200 {"app":"openmausbot"}

GET https://your-public-host.example:8443/
→ 200，933 字节

GET https://your-public-host.example:8443/pair
→ 200

GET https://your-public-host.example:8443/api/bots
→ 403 {"error":"forbidden: this request came through a proxy (pair this device to use the server remotely)"}

GET https://your-public-host.example:8443/.well-known/openmausbot/environment
→ 200，version 0.1.143，platform darwin
```

403 是**预期行为**，不是故障：反向代理进来的请求被识别为 `proxied`，
按 `request-auth.js` 的规则必须走配对，不能继承本机 loopback 的 owner 权限。

### 期间发现并修复的故障：`forbidden: cross-origin request`

首次手机发消息失败，界面红色提示 `forbidden: cross-origin request`。

**根因**：Caddyfile 里写了 `header_up Host {upstream_hostport}`，注释还写着"保留原始 Host"，
但该指令实际把 Host **改成了**上游地址 `127.0.0.1:9001`。
OpenMausBot 的 `requestOrigin()` 据此算出请求来源为 `https://127.0.0.1:9001`，
与浏览器 Origin `https://your-public-host.example:8443` 不一致，于是 cookie 会话被判跨站。

**修复**：删掉该行（Caddy 的 `reverse_proxy` 默认保留客户端原始 Host）。

**修复前后对照**：

| 检查 | 修复前 | 修复后 |
| --- | --- | --- |
| cookie + 同源 Origin | 403 cross-origin | **200** |
| 未配对请求 | 403 | **403（未放松）** |
| 恶意跨站 `evil.example.com` | 403 | **403（未放松）** |
| 公网健康检查 | 200 | 200 |

关键点：修复只放行了真正的同源请求，**没有放松安全边界**。

### 非阻塞观察：`GET /api/instances → 403`

手机端会尝试读实例列表并被拒。这是设计使然——`CLIENT_ALLOW` 白名单不含该路由，
client 权限只做聊天和审批，不能改设置。不影响使用。
