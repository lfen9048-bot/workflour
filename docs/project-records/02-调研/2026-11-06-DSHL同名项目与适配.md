# DSHL 同名项目与适配

用户提供名称“dshl”，要求查看。检索发现三个独立的同名或近名仓库；截至本次调研，用户没有提供具体仓库链接，不能把其中一个确定为用户所见项目。本轮仅阅读文档、许可证、GitHub 元数据和发布资产，没有安装、运行候选或修改现有配置。

## 与当前目标的关系

当前目标是模型、skills 分开配置，同时在一个 Harness 桌面端查看工作记录。已有基线见 [05-验证/2026-11-06-双Agent最小系统复核](../05-%E9%AA%8C%E8%AF%81/2026-11-06-%E5%8F%8CAgent%E6%9C%80%E5%B0%8F%E7%B3%BB%E7%BB%9F%E5%A4%8D%E6%A0%B8.md)。

DSHL 候选主要提供启动器、运行时或实例管理能力。多开、独立数据目录、切换 profile、启动日志、AI 会话历史和 Agent 协作调度是不同能力，不能互相替代。

| 仓库 | 实际定位 | 平台与许可 | 对本项目的意义 |
| --- | --- | --- | --- |
| [hibays/DSHL](https://github.com/hibays/DSHL) | Rust 轻量启动器，管理 dsh 启动、更新、托盘与 profile 切换 | MIT；Windows、macOS、Linux 有发布包 | 可作 Mac 上的启动外壳；没有文档证据证明它提供跨实例会话聚合或完整 Agent 编排 |
| [rootkiller6788/dsh-launcher](https://github.com/rootkiller6788/dsh-launcher) | 运行时、多实例、provider、插件、skills、MCP 的管理器 | MIT；本次可见最新发布包仅 Windows x64 | 最接近“多个隔离 Harness 的管理器”；各实例独立 DSH_HOME，与现有共享会话目录方案有区别 |
| [Loliyer520/DSHL-Deepseek-Harness-Launcher](https://github.com/Loliyer520/DSHL-Deepseek-Harness-Launcher) | 基于 PCL2 的启动器发布与反馈仓库，管理 WSL 中的 Harness | Windows 10/11 64 位、.NET 4.8、WSL2；当前专有许可、源码未公开 | 可以了解其多实例与整合包设计，但目前不能称为源码开放的候选，且不直接适用当前 Mac |

三个仓库的 GitHub 元数据均未标为 fork，也未相互重定向。管理上游运行环境不等于修改了上游 Harness 源码。

## hibays/DSHL：支持当前 Mac 的轻量启动器

- README 支持复用或准备 dsh 环境、运行 dsh web、窗口与系统托盘、升级和进程监督。
- `[dsh] flags` 可以传入 `--profile`；控制面的 `switch-profile` 会持久化选择并触发重启。切换 profile 不等于同时运行不同 Agent。
- 每个启动器进程管理一个 dsh。启动器默认 `[ui] single-instance = true`；允许启动器多开需关闭此限制。另一项 `[dsh] single-instance` 控制是否拒绝已有 dsh 进程的情况，不能混淆。
- 多进程本身不会证明配置、skills、会话目录已自动独立，仍需核对实际传入的配置。
- [v0.3.0](https://github.com/hibays/DSHL/releases/tag/v0.3.0) 发布于 2026-09-29，提供 macOS Apple Silicon 与 Intel 的 dmg/zip，以及 Windows、Linux 的对应架构资产。
- 没有从 README 中找到跨实例 AI 对话聚合、角色 skills 管理和自动协作编排的承诺。

依据：[README](https://github.com/hibays/DSHL/blob/main/README.md)、[MIT LICENSE](https://github.com/hibays/DSHL/blob/main/LICENSE)、上述 Release。元数据最后 push 为 2026-09-29，未归档；这些信息只说明可见更新情况，不保证后续维护。

## rootkiller6788/dsh-launcher：隔离实例管理器

- README 明确支持安装多个 DSH runtime，每个实例固定运行时版本，运行未经修改的上游版本。
- 实例可以创建、重命名、克隆、删除、切换；每个实例拥有独立 `$DSH_HOME`。
- 管理 provider、插件、skills、MCP、整合包，支持嵌入式 Harness 窗口和进程输出。
- SQLite 中的 launch history 记录启动/退出时间与退出、崩溃状态。这是运行记录，文档没有证明它能统一查看各独立实例的 AI 对话。
- 默认数据目录为 `%LOCALAPPDATA%/AIHarnessLauncher/`；文档还涉及 Windows Credential Manager、WebView2 和 MSVC。
- README 平台徽章包含 macOS，但下载和构建说明主要面向 Windows。[最新可见发布 v0.1.0](https://github.com/rootkiller6788/dsh-launcher/releases/tag/v0.1.0)（2026-09-07）仅有 `DeepSeek-Harness-Launcher_0.1.0_x64-setup.exe`。不能据徽章称其已有可下载的 Mac 版本。

依据：[README](https://github.com/rootkiller6788/dsh-launcher/blob/main/README.md)、[MIT LICENSE](https://github.com/rootkiller6788/dsh-launcher/blob/main/LICENSE)、上述 Release。仓库最后 push 为 2026-09-16，未归档。

## Loliyer520 的 DSHL：当前源码未公开

- README 描述 WSL 环境准备、多个实例并行、崩溃恢复、dsh web/tui/headless、版本管理、插件与 dspack 整合包等能力。
- 同一 README 明确写明源码开放属于计划；[LICENSE](https://github.com/Loliyer520/DSHL-Deepseek-Harness-Launcher/blob/main/LICENSE) 是“最终用户许可协议（专有软件）”，当前源码不公开，二进制可免费使用与分发原版，但有限制商业使用等条款。
- GitHub 有仓库与免费下载不代表源码已经开放。

依据：[README](https://github.com/Loliyer520/DSHL-Deepseek-Harness-Launcher/blob/main/README.md)、上述 LICENSE。仓库最后 push 为 2026-09-24，未归档。

## 当前适配判断与缺口

- 对当前 Mac，hibays 是已核实有发布包的候选；rootkiller 的实例管理更接近此前“隔离 Harness”描述，但当前发布平台有缺口。
- 独立 DSH_HOME 会把配置与数据分开；不能套用现有“共享 ~/.dsh/sessions，桌面统一查看”的结论。跨实例统一会话界面仍需实际证据。
- 三者与现有 WorkBuddy 插件、额度、两个 Agent 的配置及旧会话兼容性均未实际测试，不承诺能直接复用。
- 三者的启动器能力不直接决定多个 Agent 如何拆任务、交接代码和维护文档。
- 尚未作出采用、安装或迁移决定；具体仓库仍待用户后续链接或界面特征确认。当前任务止于调研。

## 后续接入评估：助手建议，尚未选型

用户追问“这几个开源项目能接入我们的计划吗”。本次复用当日调研，重读当前需求、记录和实际启动脚本，并再次核对 hibays 与 rootkiller 的 README。未安装或修改配置，未运行候选或发起模型请求。

- **现有执行层继续复用**：两个 CLI 已经完成模型、自动 skills 清单分开及原 Harness 桌面读取历史的验证。当前尚未确定、也未完成的是任务分配、代码与文档的接力和结果交接。
- **hibays/DSHL 可选接入启动层**：有 Mac 发布包，适合以后需要托盘、启动与版本管理时采用；现有 headless profile 并不是 web 界面，不能保证把现有脚本或 profile 直接填入就有新窗口。
- **rootkiller/dsh-launcher 暂不优先接入**：实例与生态管理更完整，但当前发布平台与本机不符；独立 DSH_HOME 可能使会话不再写入现有共享目录，统一历史需重新核对。不能把它的启动历史当成 AI 会话聚合。
- **Loliyer 的 DSHL 当前不建议接入**：Windows/WSL 且源码未公开，对当前 Mac 的需求没有明确优势。
- **若连同此前候选考虑，OpenMausBot 更值得验证统一入口**：文档提供自定义 ACP 引擎，存在 `OpenMausBot → Harness ACP profile → WorkBuddy` 的候选路线，但整条链路未验证；现有 headless 脚本不能直接充当 ACP 服务。OpenMausBot 有自己的记录库，不能替代“原 Harness 桌面统一查看”的要求，除非用户后续决定调整统一入口。见 [02-调研/2026-11-06-OpenMausBot调研](2026-11-06-OpenMausBot%E8%B0%83%E7%A0%94.md)，来源为该笔记所引的 [custom-engines.md](https://github.com/milind-soni/OpenMausBot/blob/main/docs/custom-engines.md)。
- **MoA+ 作为协作机制参考**：其协调者/Worker 与代码、文档分工更接近目标，但要求另一套兼容环境，Worker 各自模型与 skills 的配置仍有缺口，当前不建议直接替换已验证的执行层。见 [02-调研/2026-11-06-Harness社区分支和扩展候选](2026-11-06-Harness%E7%A4%BE%E5%8C%BA%E5%88%86%E6%94%AF%E5%92%8C%E6%89%A9%E5%B1%95%E5%80%99%E9%80%89.md)。

建议的最小方向是：现有 CLI 作为执行层，后续按需要添加一个协调入口；DSHL 仅在启动或实例管理出现实际需求时采用。用户仍要求原 Harness 桌面作为统一查看入口时，应以保留该行为为约束，不把采用 OpenMausBot 或迁移历史当成已确认决定。

若用户后续授权试接，建议先验证一个 Agent 的 ACP 链路、原 provider/skills 是否保留，以及新会话在两个界面的实际可见性；此处只是候选验证范围，不是已经开始的计划。
