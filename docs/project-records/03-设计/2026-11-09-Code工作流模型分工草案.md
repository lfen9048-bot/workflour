# Code 工作流模型分工草案

最新进展：用户授权试运行后，已新增独立DeepSeek编码配置，并与Gemini完成真实咨询、代码修复、独立审核和自动回传；最终11项测试通过。Codex用当前窗口协调，原GLM/Doc保留。此次小试验支持此分工可运行，不构成模型排名或永久角色承诺。见 [04-搭建/2026-11-09-实测DeepSeek与Gemini讨论协作](../04-%E6%90%AD%E5%BB%BA/2026-11-09-%E5%AE%9E%E6%B5%8BDeepSeek%E4%B8%8EGemini%E8%AE%A8%E8%AE%BA%E5%8D%8F%E4%BD%9C.md)；以下初次盘点/建议中的“未执行”属于当时阶段。

## 用户本次明确的目标

用户表示现在开始正式搭建工作流，第一套是 code 工作流，要求综合现有模型建议分工。本篇是助手建议，不是已确认的永久角色配置。本轮只读盘点与记录，没有修改 Bot、模型、skills、服务或调用候选模型。

同日用户进一步提出倾向：“由 codex 做总控，deepseek 和 gemini 做主力编程或审核”，并询问 V4.1 Flash 主编码是否更好。以下已按此方向修订，替代上一版“GLM 主编码、DeepSeek 主要文档”的建议。用户明确的是倾向和重新评估要求，具体角色配置尚未执行。

## 当前建议：Codex 总控，DeepSeek 与 Gemini 交叉实现和审核

| 职责 | 建议承担者 | 具体交付 |
| --- | --- | --- |
| 需求、方案和总控 | 当前 Codex 对话，与用户一起 | 验收条件、方案、任务拆分、选定每项任务的实现者和审核者、处理分歧和组织交接 |
| 默认主要编码 | DeepSeek-V4.1-Flash，独立omb-deepseek-coder | 实现明确任务、单元测试、修复问题；已在讨论演练完成修复与11项测试，大项目表现仍需观察 |
| 默认独立审核，兼另一名编码主力 | Gemini 3.8 Flash High / 现有 Gemini | 按需求读真实代码、找反例和测试盲区；由 Gemini 主写时改由 DeepSeek 审核 |
| 执行验证与整合 | 协调者调用测试/构建工具 | 重跑测试、核对需求覆盖与代码快照、检查审查问题闭环；不用模型口头结论替代执行结果 |
| 文档和交接整理 | 保留现有 Doc，独立会话 | README、使用示例、接口说明和交接记录；根据代码和测试整理，不承担自己所写代码的独立审核 |
| 替补和按需增援 | GLM / Claude 等 | GLM 已验证链路作为备用；Claude 尚待验证，不作为每个任务的固定必经阶段 |
| 最终产品验收 | 用户 | 判断功能是否符合实际目的 |

常规路线：用户目标 → Codex 整理规格和任务 → DeepSeek 实现和自测 → Gemini 独立审核并提出反例 → DeepSeek 修复 → Codex 组织实际复测和整合 → Doc 整理文档 → 用户验收。

另一条路线：Codex 分配某项任务给 Gemini 实现 → DeepSeek 独立审核 → Gemini 修复 → Codex 组织验证。页面/交互或需读设计图的任务可优先尝试此路线，但不是已证明 Gemini 全面优于 DeepSeek，也不等于当前 ACP 已验证图片输入。角色按任务固定，不在同一轮中随意互换。审核意见必须有代码位置、失败场景或测试证据；有分歧由 Codex 复现并处理，不以多数投票通过。

上一版主要根据 GLM 已跑通而分配主编码，没有同题横评证明其优于 DeepSeek。此次官方资料支持将 V4.1 Flash 作为编码主力候选，但尚未证明 WorkBuddy 当前路由的确切后端修订版或本地项目表现。首次实战应比较明确的功能、Bug 修复和多文件修改任务，记录通过率、有效审查发现、返工、耗时和可见额度，再调整默认实现者。

当前 omb-doc 的 persona 和自动 skill 为 Doc/doc-writer；该 skill 只有角色说明，不是工具或文件权限限制。落地时应新建 DeepSeek 编码 profile，或将现有 Coder 的模型切换后开启新任务；保留 Doc，避免混用长文档会话。无需安装另一版 Harness。当前薄 code-assistant/doc-writer 也不能替代完整任务规则和验收条件。本轮仅修订建议，未执行这些配置操作。

Codex 若直接参与实现，应由 Gemini 或另一独立角色审查；审查阶段先提交问题和复现证据，不同时改写同一批业务文件。当前共享目录采取单一写入者；需要并行编码时先拆文件范围或独立 worktree。交接统一读写项目材料，不依赖聊天自动共享。

## 其余模型如何纳入

- GLM 5.3、GLM 5.3 Flash、DeepSeek V4 Pro：作为备用和对比对象，不占默认主流程；不凭非 Flash/Pro 名称直接升级。
- Kimi K3 / K3.1 Pro：候选前端实现和读设计稿任务；官方 WorkBuddy 文档对 Kimi K3 描述偏向前端和多模态，但本地 Harness 输入、工具链和实际效果仍需验证。
- HY3 / HY4：可测试需求整理、中文说明等辅助工作，暂不增加与现有 Doc 重复的常设角色。
- MiMo、Space-Bunny、MiniMax、GPT-OSS：先放候选清单。部分只是缓存或未启用，不为“用完所有模型”增加固定阶段。
- 选择标准：同一任务、相同输入与验收条件，比正确性、审查发现的有效问题、返工轮数、耗时和可见额度；记录真实返回的模型，优先按角色替换，而不增加冗余角色。
