## 用户看到的工作方式

每个项目有自己的协作群，每个功能或问题有独立话题。用户可以查看讨论、点名提问和打断。Codex组织和总结；DeepSeek/Gemini可以互相咨询，并在同一项任务上分别担任实现者和审核者。

| 场景 | 如何讨论 | 结束时留下什么 |
| --- | --- | --- |
| 开始前讨论方案 | Codex给目标和验收条件；DeepSeek提出实现思路；Gemini提出遗漏和风险；Codex定案 | 方案、任务和接口约定 |
| 编码中求助 | 当前实现者向另一方提出具体问题，附相关代码和已尝试方法 | 建议或复现结果；原负责人继续推进 |
| 审核与返工 | 审核者给代码位置、失败场景或测试；实现者修复或提供反证 | 问题处理状态、新代码和新的审查/测试证据 |
| 争议处理 | 双方说明证据与剩余分歧，Codex复现或补充测试后决定 | 采用方案、理由和未解决问题 |
| 完成汇总 | Codex核对需求和实际测试，Doc可整理交接说明 | 交接文件、验收材料和下一步 |

示例：DeepSeek提出实现A → Gemini指出某输入会失败并给出用例 → DeepSeek修复 → Gemini复核 → Codex组织重跑测试并记录结论。

## 每次讨论的最小信息

一条咨询/委派带任务编号、发起者、接收者、当前问题、相关文件/代码快照、期望答复，以及是否允许改代码。普通进度公告只显示，不触发所有Bot回复；需要行动时使用实际委派或定向点名。

角色和任务分开：同一项任务只有一个实现负责人，另一方审核；求助不自动转移写入权。审核先提交问题和证据，不与实现者同时改同一批文件。需要并行实现时先划分文件范围或独立worktree。

咨询、正式审核、派发实现和公告要分别表达。现成consult只是咨询语义，不是强制只读沙箱；需要读代码、执行检查的正式审核应明确交付和允许动作。现有原生委派已有去重、祖先回派与交叉等待保护，不绕过它另起无限循环。

## 让讨论有结果

- 默认定向唤醒，不让每条消息触发所有成员。
- 简单修正可直接执行和审核，不强制开方案会。
- 建议每个议题最多三轮意见往返；重复观点、超时或仍未解决时交Codex处理。此为本项目拟定规则，尚无程序级硬限制，不声称现有提示词即可保证不循环。
- 群聊原生的一轮接力限制与上述“三轮议题”不同。多轮应由主持者明确继续，不能为了讨论取消已有保护。
- 结论必须写入现有`.workflour/handoff.json`的decisions/blockers/next_action和相关spec/plan/review；讨论记录不能替代测试证据或用户验收。
- 代码改动后重新审核/测试，旧快照不得继续放行。
- 用户打断后停止当前讨论，恢复时读取已记录状态，避免重复派工。

下一次最小端到端验证应使用独立演练话题：

2. 验证DeepSeek能向Gemini发一次只读咨询，Gemini真实收到并回复，结果回到发起者。
3. 验证群中点名、公告不唤醒、忙碌排队/中断，并检查不会重复发相同任务。
4. 验证Codex外部协调入口的身份和目标线程，形成可见的统一总结；当前窗口不能冒充已接入群的常驻Codex Bot。
