# 复查现有链路与分离边界

## 目的

响应用户“逐项验证已经跑通的有没有问题”，并澄清是否分出了多个 Harness 版本。本轮没有新增功能，因此复用已有实施依据、脚本和本机源码，无需重新选型。

## 已执行

1. 独立只读核对实际 profile、项目模板及六个旧基线文件。
2. 重跑现有 ACP 握手与示例4项测试。
3. 让 Coder 实读新输入、运行现有测试、写新交接，再让 Doc 实读交接并独立复核、写说明。
4. 对 Gemini 实测审批、中断、工作目录内 shell 读取；保留目录外审批未完成的首次尝试。
5. 只读检查公网证书、页面、未配对限制、隧道、Caddy和原443服务。
6. 在全部Bot空闲后重启 OpenMausBot，核对存档，分别测试工具数据细节恢复与显式聊天口令恢复。
7. 发现助手执行会话回收 nohup 服务后，用原固定版命令在持久前台终端恢复，最终本机与公网均200，并同步服务pidfile。
8. 清理示例目录的一次性新文件至证据目录，原文件哈希未变；更新首页及过时的需求范围描述。

## 核心结论

- Harness 是同版程序的多profile；模型和自动skills分别配置并动态验证。不是多套独立安装，也没有分开账号或按角色划文件权限。
- 核心手动接力可用；没有发现串模型/skills。Gemini能用，审批等待和慢响应需要预期管理。
- 重启后历史和聊天文本可续接，但工具读取细节未必恢复，交接文件仍必要。
- 助手后台启动存在会话回收限制；当前以前台方式恢复，后台运行方式仍可后续加固。本轮未实施新守护或开机自启。

## 停止位置与下一步

本轮复查完成；服务恢复、三个目标Bot为ask且空闲。手机实机操作和强制隧道断线没有重复测试，旧记录保留。下一步由用户选择：先加固后台启动/上下文交接，或进入真实小项目；不自动扩大范围。
