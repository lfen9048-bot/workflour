# 部署 VPS 公网 HTTPS 入口

## 目的

把 Mac 上的 OpenMausBot 暴露到公网 HTTPS，供手机在蜂窝网络访问。
前置核验见 [05-验证/2026-11-08-VPS自建入口前置核验](../05-%E9%AA%8C%E8%AF%81/2026-11-08-VPS%E8%87%AA%E5%BB%BA%E5%85%A5%E5%8F%A3%E5%89%8D%E7%BD%AE%E6%A0%B8%E9%AA%8C.md)，本轮进入实际部署。

## 用户确认的方案

2026-11-09 用户选择：

- **端口**：用 8443 做 HTTPS，80 做证书验证（不动 443 的 xray）
- **常驻方式**：先手动跑，验证通了再考虑开机自启

## 为什么不能用 443

前置核验时只记录了"443 被 xray 占用"，本轮读到实际配置才发现更硬的约束：

```text
protocol: vless  port: 443
security: reality  network: tcp
dest: www.postgresql.org:443
serverNames: ['www.postgresql.org']
fallbacks: 无
```

REALITY 没有配 fallback，会把所有非 VLESS 流量伪装转发到 `www.postgresql.org:443`。
Caddy 若抢 443，会直接打断用户正在用的代理。所以改走 TCP 8443。

补充：UDP 8443 被 sing-box 占用，但 **TCP** 8443 空闲且实测公网可达。

## 实际链路

```text
手机 --HTTPS:8443--> VPS(Caddy + Let's Encrypt) --127.0.0.1:9001--> [ssh -R] --> Mac:8799
```

证书走 80 端口 ACME HTTP-01，不占 443。

## 部署步骤与结果

### 1. 端口可达性实测（修正前置核验的"未验证"项）

在 VPS 临时起响应服务，从 Mac 用 `curl --noproxy` 直连：

| 端口 | 结果 |
| --- | --- |
| TCP 80 | 返回 `PROBE-OK`，公网放行 |
| TCP 8443 | 返回 `PROBE-OK`，公网放行 |

测完已清理进程与临时日志。

**方法学教训**：一开始用 `nc -z` 探测，它对不可路由的 `192.0.2.1:80` 也报"可达"，
说明结果被本机 Clash 的 TUN 劫持，不可用。改用 curl 直连并加 `--noproxy '*'` 才可信。

### 2. VPS 安装 Caddy

```sh
apt-get install -y caddy    # 2.6.2-6ubuntu0.24.04.3
```

默认 Caddyfile 占 `:80`，已备份为 `/etc/caddy/Caddyfile.orig.20261108-142652`。

### 3. 写入反代配置

配置归档在 `integrations/openmausbot/vps/Caddyfile`，已与 VPS 实际配置比对一致（忽略注释）。

**踩坑 1：HTTP/3 抢 UDP 8443**

首次 `systemctl restart caddy` 失败：

```text
Error: loading initial config: listen udp :8443: bind: address already in use
```

原因：Caddy 对 `:8443` 默认同时开 HTTP/3（UDP），撞上 sing-box。
修复：全局 `servers { protocols h1 h2 }`，只用 TCP 上的 h1/h2。

**踩坑 2：sshd 的 GatewayPorts 反而是好事**

`GatewayPorts` 未显式设置，默认 `no`，所以 `ssh -R` 只能绑 `127.0.0.1`。
Caddy 就在 VPS 本机反代 `127.0.0.1:9001`，正好匹配，**不用改 sshd**。

### 4. 证书签发

重启 Caddy 后自动完成：

```text
validations succeeded; finalizing order
certificate obtained successfully  identifier: your-public-host.example
```

从 Mac 验证：

```text
subject=CN=your-public-host.example
issuer=C=US, O=Let's Encrypt, CN=YE2
notBefore=Nov  8 13:29:18 2026 GMT
notAfter=Feb  6 13:29:17 2027 GMT
ssl_verify_result=0
```

### 5. Mac 侧服务与隧道

服务需带 `--public-url`，否则配对链接里没有公网地址（`/api/auth/pairing` 返回 `publicUrl: null`）：

```sh
node <cli> serve --port 8799 --no-pair --public-url 'https://your-public-host.example:8443'
ssh -N -R 127.0.0.1:9001:127.0.0.1:8799 root@<YOUR_VPS_IP>
```

**踩坑 3：nohup 起的隧道被会话回收，裸 ssh 也会被远端关闭**

第一次用 `nohup ... &` 起的 ssh，14 小时后发现进程没了，公网 502。
改用后台作业方式后仍会断，退出码 255，stderr 只有 `Connection to <YOUR_VPS_IP> closed by remote host.`

判断：本机 Clash 的 TUN 接管 SSH 连接，代理重连时把长连接切断。
VPS 侧 sshd 日志显示正常接受连接，`fail2ban` 未启用，排除被封禁。
另有境外 IP 在暴力破解 SSH，属背景噪声，与本次断开无关。

**最终修复**：脚本改用 `while true` 守护循环，断开后 5 秒自动重连。
实测杀掉 ssh 子进程后，守护在 5 秒内重建隧道，公网恢复 200：

```text
2026-11-09 13:53:17 隧道断开 (exit 0)，5 秒后重连
→ 公网: 200
```

**踩坑 4：隧道可能没有 pidfile**

手工或后台作业起的隧道不会写 pidfile，脚本 `up` 会误判并重复建一条，
导致 VPS 上 9001 端口冲突。已在脚本里加 `find_tunnel_pid()` 兜底识别。

## 后续加固：彻底脱离厂商服务（2026-11-09 下午）

用户要求"网站走自己的，和作者服务商没有关系"。核查后确认现状**已经满足**，只做了两处加固。

### 核查结论：当前没有连厂商服务器

运行中的服务进程全部网络连接：

```text
127.0.0.1:8799  LISTEN
127.0.0.1:8800  LISTEN
→ 无任何外部连接
```

整个代码库只有 1 个厂商域名 `accounts.openmausbot.com`，且**只在两种模式下被调用**：

| 命令 | 是否连厂商 |
| --- | --- |
| `openmausbot login` | 会（发邮箱验证码） |
| `serve --tunnel` | 会（申请托管地址） |
| `serve` 本地模式 | **不连** |
| `serve --public-url` + 自建反代 | **不连** |

本项目用的是最后一种，所以厂商链路从未被激活。

### 加固 1：npx 改为全局安装

原先用 `npx --yes openmausbot@0.1.143`，每次启动可能联网拉包。改为：

```sh
npm install -g openmausbot@0.1.143
```

- 安装位置：`/opt/homebrew/lib/node_modules/openmausbot`
- 入口：`/opt/homebrew/bin/openmausbot`
- Homebrew prefix 可写，不需要 sudo
- `scripts/omb-public.sh` 已改为优先找全局路径，npx 缓存仅作兜底

验证：服务进程命令行确认是 `/opt/homebrew/lib/node_modules/openmausbot/dist-server/index.js`。

### 加固 2：删除厂商账号凭据

`~/.openmausbot/tunnel-account.json` 是 2026-11-08 21:20 `login` 留下的（含邮箱 `lfen9048@gmail.com`、accountToken、installationId 等 7 个字段）。

由于 `--tunnel` 从未被调用，该文件是死文件，且是**与作者服务商唯一的关联点**。经用户确认已删除。

删除后服务、公网入口、Bot、配对会话全部正常，`openmausbot status` 也不再输出账号信息。
