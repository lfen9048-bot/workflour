# 实施DSH多模型Code工作流

## 用户确认与架构纠正

本轮用户提出具体实践分工，经选择确认后明确“Implement the proposed plan.”。

- Kimi K3.1 Pro、DeepSeek V4.1 Flash、GLM 5.3 通过 **DSH 加 dsh-connect-workbuddy 插件**调用。WorkBuddy只提供模型/额度通道，不是另一个Agent，不启动独立WorkBuddy工作流。
- Antigravity保留独立Agent，采用当前已实测的Gemini 3.8 Flash High；用户明确其为主编码，DeepSeek承担可并行子任务。
- Kimi主持规划，DeepSeek和GLM参与；GLM规划与GLM独立审核使用不同角色配置及Bot/会话。
- 总控为当前Codex窗口；计划在原需求范围内且无阻塞时自动进入编码，不增加逐阶段用户确认。新需求或影响目标的未决分歧交给用户。
- 第一轮选择独立小项目验证，报告Agent和报告阶段暂缓。最终产品验收仍由用户决定。
- 一个项目有共同需求、计划、决策和交接；Agent工作记录分开保存，可按需读取并标注来源。Obsidian用于统一查看，不把新会话或角色配置误称为权限隔离。

以上替代早期“DeepSeek默认主编码、Gemini默认审核、GLM备用”的角色建议；旧记录保留作历史。

## 已完成：角色配置与协议验证

新增三个独立profile与OpenMausBot实例：

| 角色 | Profile/实例 | 实际选中路由 |
| --- | --- | --- |
| 规划主持 | omb-kimi-planner | workbuddy / kimi-k3.1-pro |
| 规划风险检查 | omb-glm-planner | workbuddy / glm-5.3 |
| 独立代码审核 | omb-glm-reviewer | workbuddy / glm-5.3 |

`integrations/openmausbot/setup.sh --only ROLE`支持三个新增角色，`run-acp-agent.sh ROLE`继续复用现有ACP原生恢复桥接。默认setup仍保留原Coder/Doc/agy范围；原headless入口没有修改。三个角色各有独立技能目录，旧角色和会话保留。

实际生成后，无prompt ACP的initialize/session-new/session-close均成功，stdout纯JSON-RPC，进程正常退出。此结果仅证明协议和选中路由，不单独证明模型推理与工具调用能力。

证据：三角色握手（本机私有材料，未上传）。配置离线测试4项通过，覆盖独立模型和技能、原配置保留、账号状态幂等保留、未知参数拒绝及文件权限；启动脚本语法检查通过。

## 已完成：工作流工具包与独立复核

新增可选`--workflow code-team`模式；旧manual流程保持兼容。三方规划需有各自的非空记录并收敛为计划，编码工作项明确负责人和文件归属。审核者不得为任何编码者；`docs_required:false`可跳过报告但不跳过测试与用户验收。

独立复核发现并已由作者修复：编码工作项中已知文件若漏出`code_files`，原本可能不进入审核/测试快照。现实现阶段起要求两份文件集合一致。临时项目实测遗漏文件被拒绝；补入文件后旧审核失效；重置审核快照后旧测试仍失效；次编码者以大小写/空格变体自审也被拒绝。未知workflow类型拒绝，不静默退回manual。

工具包作者报告17项检查器与5项初始化测试通过；独立复核没有修改真实演练目录。最终根目录完整回归48项全部通过，日志保存在实测证据`workflow-regression-48.txt`。

## 已完成：真实小项目演练

独立项目 `examples/code-team-demo` 已完成真实模型协作，当前阶段为 `acceptance`，用户验收为 `pending`。

1. Kimi、DeepSeek、GLM各自独立提出方案；Kimi通过原生 `coordinate_bots` 向两位同伴咨询，完成1轮讨论并写入最终PLAN。两项consult都真实执行一次、完成、回传并恢复父任务；不是用Codex代写模型意见。
2. Codex核对计划在需求范围内，计划门通过后直接派发。Antigravity与DeepSeek在独立新任务会话中并行启动，前者负责CLI与CLI测试，后者负责存储与存储测试，文件归属互不覆盖。两者实际读取共享README/AGENTS/HANDOFF/PLAN；新原生session与旧会话不同。
3. DeepSeek存储层48项测试通过。Antigravity首轮测试发现自身测试文件的中文bytes字面量语法错误，自行修正后59项联合测试通过。
4. 与规划者不同Bot/新会话的GLM Reviewer独立读四个文件、实际跑59项测试，并在临时目录验证中文、非法ID、损坏JSON不覆盖、缺失文件和退出码，结论PASS，无产品级返工要求。
5. Codex独立复跑59项产品测试，加5项真实CLI进程探针，全部退出0。审核与测试四文件SHA256一致，acceptance阶段检查通过。用户尚未验收，不能标记done。
6. 另设已知缺陷样例验证退回路径：GLM发现bool误判为合法ID并REQUEST_CHANGES，DeepSeek修复，GLM复审PASS，Codex独立10断言通过。此为合成样例，不能冒充产品发现了漏洞。

工作记录在项目 `records/` 各角色目录；可读会话导出使用新脚本 `scripts/export-agent-record.py`，只导出可见文本/工具名与结果标记，不复制原生trace或隐式推理。公开文本脱敏是best-effort，不宣称任意秘密都能自动识别。

## 实测中的限制与协调干预

- Antigravity起初重复检查目录、做argparse小实验，命令真实成功但推进慢。Codex在只读试验等待审批时安全中断两次，让排队的严格短prompt进入执行；之后完成编码。全过程仅对具体操作allow-once，未启用full/always。该结果是**有人协调的协作流程**，不是无人值守调度器。
- OMB拒绝显式选择`gemini-3.8-flash-high`，通过其允许的`agent-default`入口新建后，真实`session/new`的`currentModelId`报告`gemini-3.8-flash-high`；另一个配置项标识为`gemini-3.8-flash`，两者均如实保留。没有把缓存默认值当作实际模型证据。
- 会话摘要digest会包含同目录其他Agent同期改动，不能据此判断文件作者；所有权以分工和真实写入行为为准。
- 新任务、独立日志与共享文件交接已验证，但不是文件权限沙箱，也不承诺完全清除全局记忆。没有实施常驻Codex、运行中崩溃恢复、自动报告或部署。
