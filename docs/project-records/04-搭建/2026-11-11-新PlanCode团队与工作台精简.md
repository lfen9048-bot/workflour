## 流程与已实现机制

`大管家转交 → Plan 负责人调研初案 → Plan 评审 → 负责人定稿 → 一位主编码 → 独立技术审核 → Plan 实际体验 → 用户验收`。

- Plan 负责人是共享账本与 handoff 唯一维护者；自己研究/定稿使用本地 record，有证据哈希和代码快照，不伪造委派。
- 派单 claim/token/receipt/result 持久化。新 `plan-code` 与旧 code-team 分支并存，旧账本不补跑或改版本。
- 默认单主编码；可选 helper 要有独立子任务及范围。首次可看页面由主编码向非祖先 Plan 评审做一次方向咨询，原生回传后继续同一实现任务。
- 技术与产品返工共享两轮；故障恢复每阶段/角色最多一次 retry，停止后须有对应的新继续来源。等待模型、等待审批不重派。
- worker 通过 `check.py test --files ...` 产生独立测试证据，负责人导入；代码改变后旧审核、测试和体验均失效。
- 网页体验必须真实浏览器交互、逐验收目标观察、桌面/手机截图和文件哈希。纯 CLI 项目明确 product_surface:cli 后用真实命令/结果，不伪造截图。
- 最终停 acceptance/pending。检查器核对材料一致性，不证明用户身份、完整覆盖或观察真实性。

## 15:47 实际返工暴露的补充回执边界

真实演练中，维护者在第 1 轮返工期间补充了满额提示的复现证据。Plan 负责人向原主编码 thread 追加具体修复，原生返回第二条 queued assignment。源码确认本机 ACP adapter 没有即时 steer，原生服务会等待该 thread 上一回合结束再执行，所以这是同一业务返工的串行补充；不能说只有一条原生派单，也不能把它当成并行重复任务删掉。

原账本只允许一 token 对应一回执，导致观察器冲突。现已增加显式 `supplement PHASE ROLE ID --reason ... --evidence ...`：由状态负责人绑定真实补充，严格核对同 sender/worker Bot 和 thread、时间顺序、不同工作 brief、原 token、来源说明哈希；原主单、轮数和原生记录不变。未登记的同 token 仍报冲突。完成和 advance 必须主单与全部补充 completed，排队中不能先复审。补充失败明确阻塞，普通 retry 不得重跑已完成主任务。

69 项相关回归测试通过（新增12项）。当前两回执只在内存副本核对，维护者没有直接写 live 账本，由 Plan 负责人使用新 CLI 登记。检查时主单 completed、补充 running，完整 E2E 仍未通过。新角色 source 与 runbook 已同步，正在运行的 live SOUL 未在本步骤修改。证据：补充回执实现与验证（本机私有材料，未上传）。
