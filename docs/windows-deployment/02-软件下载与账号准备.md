# Windows 软件安装、登录与插件

以下安装资料于 2026-11-11 复核官方入口；固定版本来自当前Mac基线。命令由负责部署的 Agent 执行；使用者只需完成账号登录和必要的安装界面确认。**命令不是要求使用者日常手动操作终端。**

首选 Windows 11 x64 原生环境。ARM64 要另行核对 DSH/AGY 安装包架构与兼容性，不算本次已确认基线。不首选 WSL：WorkBuddy 的 Windows 登录状态与原生路径在 WSL 中不能假定自动可用。

## 1. 基础软件

| 软件 | 建议 | 官方来源 | 检查 |
| --- | --- | --- | --- |
| PowerShell | 7 稳定版；不要混用 Bash 语法 | [Microsoft 安装文档](https://learn.microsoft.com/en-us/powershell/scripting/install/install-powershell-on-windows) | `$PSVersionTable.PSVersion` |
| Node.js | 24 LTS 或兼容的更高版本；复刻优先 24 LTS | [Node 下载](https://nodejs.org/en/download) | `node --version`、`npm.cmd --version` |
| Python | 3.12+；部署时记录小版本并运行测试 | [Python Windows 下载](https://www.python.org/downloads/windows/) | `py -3 --version` |
| Git | Windows 官方稳定版 | [Git Windows 安装](https://git-scm.com/install/windows) | `git --version` |
| Obsidian | Windows 稳定版 | [Obsidian 下载](https://obsidian.md/download) | 能打开指定本地知识库 |

可采用官方列出的 WinGet 命令安装 PowerShell、Git：

```powershell
winget install --id Microsoft.PowerShell --source winget
winget install --id Git.Git -e --source winget
```

安装 Node/Python 后重新开终端，让 PATH 生效。Python 找不到 `py` 时用 `Get-Command python` 核对实际安装路径；不要误用仅跳转 Microsoft Store 的占位命令。启动器最终登记实际 `python.exe` 路径，不依赖偶然的 PATH。

统一源码、JSON、YAML、Markdown 使用 UTF-8。Python 子进程环境设置 `PYTHONUTF8=1`；ACP 使用 UTF-8 字节流，stdout 仅协议数据，不能在 stdout 打印 PowerShell 欢迎词或调试信息。

## 2. 安装 DeepSeek Harness（DSH）

优先从 [DeepSeek 官方下载页](https://www.deepseek.com/download/) 选择 **DeepSeek Harness 的 Windows 版本**，不是手机 DeepSeek 聊天客户端。核对当日官方页所指向的文件。

官网下载页当前提供的 Windows x64 入口：
[DeepSeek Harness Windows 安装包](https://download.deepseek.com/desktop/dsh-latest-windows-x64.exe)。2026-11-10 曾核对该 URL 的 HEAD 返回 200，本次复查官网仍有Windows入口；没有在 Windows 执行安装包。latest 会变，不代表它永远等于 Mac 的 0.2.1-rc.2。

安装后：

1. 正常打开 DSH，按产品要求完成首次设置/登录。
2. 应用菜单查找 `Manage dsh Command…`（管理 dsh 命令），安装终端命令；重新开终端执行 `dsh --version`。
3. 用 `Get-Command dsh -All` 确认指向刚装的运行时，没有被另一份 npm 安装遮住。
4. 记录 DSH Desktop 版本、CLI 版本、CLI 真实路径和 DSH_HOME。关闭窗口不一定退出进程；修改插件后按菜单真正退出再启动。

依据：[官方桌面说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/desktop/README.md)。菜单适用于当前上游，老版本界面不同则查该版本说明，不能猜固定 Windows 安装路径。

Mac 基线是 `0.2.1-rc.2`。本次核对其 GitHub Release 没有附件，**不要编造这个版本的 GitHub EXE 下载地址**。若官网 Desktop 已升级，先记录新版本，按协议与插件测试决定能否兼容。需要精确 CLI 基线时，npm 上已核对存在该版本，可以采用隔离 CLI 安装方案：

```powershell
npm.cmd install -g @deepseek-ai/dsh@0.2.1-rc.2
dsh --version
```

这是替代 CLI 获取方式，不是建议同时覆盖桌面管理的 dsh 命令。两种方式选定一种作为 ACP 入口并记录绝对路径。CLI 版可按[官方主仓库](https://github.com/deepseek-ai/deepseek-harness)使用 `dsh web`；只有 Web 时可以先验模型/ACP，桌面自动分类要另验，不能宣布桌面功能也已完成。

## 3. 安装并登录 WorkBuddy

从 [WorkBuddy 官方 Windows 安装指南](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Installation-Win-Guide) 进入 [官方下载页](https://www.codebuddy.cn/downloads/)，选择 **WorkBuddy Windows**，不是同站的 CodeBuddy IDE 或 CodeBuddy CLI。

1. 使用以后运行 DSH/后台任务的同一个 Windows 用户安装并打开。
2. 用户本人完成账号登录，确认是所需额度所属账号/区域。
3. 先确认 WorkBuddy 自己能正常完成一个很小的请求；保留非敏感版本和结果。
4. 不从 Mac 搬 token、cookie、设备身份或加密凭据。Windows 插件走本机登录发现流程。

WorkBuddy 应用是额度/登录来源。最终代码仍由 DSH 与 AGY 执行，不把 WorkBuddy 软件当作额外第八名成员。

## 4. 在 DSH 安装 WorkBuddy 插件

复用 [dsh-connect-workbuddy 上游](https://github.com/dingminhua/dsh-connect-workbuddy)，Mac 当前版本 `5.13.1`，MIT。它明确提供 [Windows 说明](https://github.com/dingminhua/dsh-connect-workbuddy/blob/main/docs/WINDOWS.md)。插件 Node 要求与本包 Node 24 基线兼容。

先验证 Desktop 单一 profile，再扩展角色：

```powershell
dsh plugin --profile desktop add dsh-connect-workbuddy@5.13.1
```

也可以在 DSH 原生插件管理界面添加同名包并核对版本。若使用 CLI Web 而非 Desktop，目标 profile 改为 `web`；不能装进 `web` 后误以为所有 `omb-*` profile 自动装好了。

安装完成后完整退出并重启目标 DSH Host。打开插件设置，使用它的本机 WorkBuddy 登录发现/账号流程，确认账号区域与 provider。若当前版本自动发现失败，按上游 Windows 文档排查，而不是在聊天里粘贴 token。

验收分三层：

- 插件加载：没有依赖/版本错误，设置页可见。
- 模型目录：能读到真实模型与思考档位，记下 provider、model ID、variants。
- 实际调用：选择 WorkBuddy 下 DeepSeek Flash 发一个短请求，再试 GLM；得到真实回复和实际路由记录。目录存在不等于调用权限/额度正常。

然后才创建 `omb-wf-manager` 等六个 DSH profile。各 profile 使用 DSH 原生插件管理/依赖安装，不照搬 Mac 的 `ln -s node_modules`。具体 ACP profile 结构见部署步骤；只有完成最小 ACP profile 后，再对它执行对应 `dsh plugin --profile omb-wf-manager add dsh-connect-workbuddy@5.13.1` 并检查组合配置。

当前上游main的安装示例已高于5.13.1；**本仓库额度桥接仅支持5.13.1，不能把最新版文档里的每项能力当成这个固定版本已有**。先固定复刻；若目标DSH必须升级插件，单独做接口与测试适配，不直接去掉版本保护。

Windows登录发现异常时，可在本机用 `dsh plugin --profile desktop exec dsh-connect-workbuddy doctor --json` 检查脱敏摘要；原始诊断可能含本机路径和账号名字，不全量上传。当前上游Windows指南说明自定义安装目录可用 `WORKBUDDY_APP_EXECUTABLE` 指向真实WorkBuddy.exe，须在固定安装版也核对支持后设置。不要读取或粘贴凭据文件。

首次 Windows 没有旧 `agent-doc` / `omb-doc` 账号块。必须从本机已经验证成功的插件登录流程初始化角色账号引用，不能直接运行依赖旧账号块的 Mac `setup.sh`。

上游近期提示过 WorkBuddy 对非官方客户端通道的限制，因此安装成功不能保证该额度通道永远可用。失败要报告真实分类；本项目已有免费及临期优先的额度策略，不另装未经验证的第三方登录补丁。

## 5. 安装 Antigravity CLI

使用 [Google Antigravity 官方 CLI 安装说明](https://antigravity.google/docs/getting-started?tab=cli)。它是独立运行时，**不能用 Gemini CLI 冒充**。

官方 PowerShell 安装命令：

```powershell
irm https://antigravity.google/cli/install.ps1 | iex
```

安装前可下载同一官方脚本审阅后再运行。不要为安装永久关闭系统安全策略。默认用户级位置由安装器决定，当前文档为 `%LOCALAPPDATA%\agy\bin`；以 `Get-Command agy -All` 为准。

```powershell
agy --version
agy
```

在原生 CLI 登录流程中由用户完成 Google 登录。随后检查：

```powershell
agy acp --help
```

官方[ACP指南](https://antigravity.google/docs/cli/acp/)当前示例为 `agy acp`，以stdin/stdout传JSON-RPC。本机Mac入口使用 `agy acp --stdio` 并带 `--disable-telemetry`；这两个flags仅在目标Windows版本help确实支持时沿用，不假定所有版本相同。不要强制下载 OpenMausBot 另一种驱动要求的 `agy_acp_server.par` 组件，本项目已用原生 CLI 的 customAcp 方式。

若当前 CLI 支持 `agy acp --login`，可按官方 [认证说明](https://antigravity.google/docs/install?tab=cli) 使用；具体 flags 以安装版本 help 为准。登录成功还要做一次 ACP 文件读取测试。

## 6. 安装 OpenMausBot

复刻基线：`0.1.143`，Node **>=24**，Apache-2.0。来源是当前安装包声明的 [milind-soni/OpenMausBot](https://github.com/milind-soni/OpenMausBot)，不要仅凭搜索出的同名项目换仓库。

```powershell
npm.cmd install -g openmausbot@0.1.143
openmausbot.cmd --version
openmausbot.cmd serve
```

打开服务实际输出的本机入口，基线是 `http://127.0.0.1:8799`。初次登录/配对按服务本机提示完成；不要把登录链接或配对码贴进部署报告。首次保持前台便于诊断，全部本地验证后再装后台托管。

推荐 CLI + 浏览器，以便与本项目方式一致。不要再额外启动一个 Desktop 内置服务占用同一端口、写同一数据目录。版本升级会影响内部 API/数据库读取适配，首轮先固定版本。

## 7. Obsidian 与 DeepSeek API

Obsidian 安装后选择“打开文件夹作为知识库”，例如 `C:\workflour-notes\多Agent协作开发工作流`。不要求额外 Obsidian 插件，工作流直接写 Markdown。

用户已有 DeepSeek API key 是最后备用，不随包传递。Windows Agent 应引导用户在目标 DSH 的原生凭据设置中配置，确认所有正式 DSH profile 能解析 `deepseek-official` provider 与 `DEEPSEEK_API_KEY` 凭据引用。**不要把密钥写进角色 patch、示例 JSON、聊天、日志或 Git。** 候选模型 `deepseek-flash` 必须由该运行时真实解析并以小请求验证。

这里的“本地 Agent”是程序和记录在电脑运行，并不表示云模型推理离线。WorkBuddy/Google/API 账号及相应额度是独立前提。


## 8. 浏览器与截图工具

Plan最终体验需要真实浏览器，不仅是测试日志。按[Playwright Python官方库说明](https://playwright.dev/python/docs/library)在Windows重建独立环境，示例：

```powershell
py -3 -m venv .tools/browser
& .\.tools\browser\Scripts\python.exe -m pip install playwright
& .\.tools\browser\Scripts\python.exe -m playwright install chromium
```

安装后记录实际版本，锁定已验证版本；不要复制Mac虚拟环境。可使用已装Chrome的真实channel或Playwright Chromium，均须实测；独立context，不读取用户Chrome profile。更新角色的BROWSER/CAPABILITIES本机路径。网页载入、交互、桌面/手机截图、图像工具读PNG都要验证；模型名支持多模态不等于插件已经传入图像。

## 9. 不是安装 Node 就自动解决的平台依赖

当前 `workbuddy/client.mjs` 另调用Ruby读取YAML，`checkin.mjs`用Python的fcntl锁，ACP入口又调用硬编码`/usr/bin/ruby`生成完整pool配置层。Windows无这些默认路径与fcntl；按第04章移植后再启用签到。UI私有runtime和部分skills使用符号链接，也须处理Windows检出/权限行为。本轮没有替Windows安装这些依赖或验证。
