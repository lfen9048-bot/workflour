# 项目协作约定

这是新项目模板。维护模板本身时，只修改已授权的模板内容；下列执行步骤面向初始化后的目标项目。

## 接手与恢复

1. 阅读 `PROJECT-WORKFLOW.md`、`.workflour/handoff.json` 和生成的 `HANDOFF.md`。
2. 按交接中的路径读取当前 feature 的 `spec.md`、`plan.md`、`tasks.md` 及当前阶段材料。
3. `stage` 表示当前要执行的阶段，不表示该阶段已经完成。接手时用 `python3 .workflour/check.py check --stage <上一已完成阶段>` 核对输入；当前阶段产物尚未生成或状态为 pending 是待做工作，不能要求它在开工前已通过。阶段完成后再检查本阶段。对非预期的缺失、过期或失败先处理，不能把材料存在当成审查、测试或用户验收已通过。
4. 核对实际文件与 `code_files`、快照及测试证据；先前聊天、模型自述和原生会话恢复都不能代替文件核对。
5. 简短说明当前任务、已完成内容、阻塞点和下一步，再继续已授权工作。

## 手动接力与职责

若 `.workflour/handoff.json` 中 `workflow.kind` 为 `code-team`，由工作台 DSH「Code Team · 总控」负责协调；优先采用
`PROJECT-WORKFLOW.md` 的 code-team 角色与记录规则。只有明确授权的协调者推进和派发，
编码者可在互不重叠的精确文件范围内并行；handoff.json 由协调者单独更新。
报告阶段可以关闭，真实测试与最终用户验收不可跳过。此模式覆盖下方 manual 的单写入者与不派发默认。

本轮默认安排可调整，不是用户此前确认的永久角色分工：协调者整理需求、拆分工作并独立验收；Coder 规划、实现、测试和修复；Gemini 独立审查；Doc 维护配套说明；用户最终验收。

- 一次只安排一个 Agent 写实现文件。Gemini 读取代码并写独立审查材料；Doc 写文档。需要改变范围时先更新任务和交接。
- 这是协作约定，不是文件权限沙箱。共享工作目录内的角色可能都有文件读写能力。
- 不自动调用 headless、不发起其他 Agent 的模型请求、不把复制提示词当成执行成功。
- 不自行改变已有模型、账号、profiles 或 skills 发现范围；添加项目 skills 时应按角色显式选择并验证实际注入清单。
- 新功能先检查本地已有内容、已有技能和工具，再读有希望的现成方案；普通纠错不重复全套选型。

## 完成与交接

- 需求要有可验证的编号和验收条件。助手建议、假设与用户确认分别记录。
- 每次阶段结束或暂停，更新 `.workflour/handoff.json`，运行 `python3 .workflour/check.py handoff`，留下下一项可执行动作。
- `code_files` 覆盖真实实现、测试和依赖配置；不包括交接、日志和纯文档。代码变化后旧审查和旧测试快照失效，必须重新审查和重跑有效测试。
- 测试由 `python3 .workflour/check.py test -- CMD ARG...` 真实执行并留下证据。命令以参数数组运行，不使用 shell 拼接。需要 shell 时单独审查明确的脚本内容。
- 独立审查的问题必须修复并复核，或明确说明接受的理由；不能只改状态而不处理问题。
- `acceptance` 表示已准备用户验收；只有记录明确用户确认来源、原话和时间后才可改为 `done`。检查器只能核对材料，不能证明记录确实来自用户。
